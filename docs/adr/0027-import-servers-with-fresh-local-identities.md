# 导入的服务器一律获得全新本地身份

Status: Accepted (2026-10-04)

从 SIP-008 文件（以及 `ss://` 文本、二维码负载）导入服务器配置时，产出的手动目录节点一律使用全新生成的身份。来源文档中的标识——`servers[].id` 的供应商 UUID、`x_shadowsocksx_ng` 扩展中按 UUIDv5 派生的分组 ID——只作为文档内装配键，用于建树时解析子引用，永不成为目录节点身份。重复导入同一份文件产生相互独立的副本，而不是合并、去重或刷新先前导入的分组。

这与订阅侧「订阅固定分组身份客户端所有」同构：目录身份属于本客户端，文档身份属于文档本身。导入是快照复制；订阅刷新才是远端数据的身份延续机制。Legacy 导入保留自己的条件采纳规则（`reusableLegacyID`），因为其来源是同一用户旧客户端的状态——是迁移，不是可分享文档。

## Considered options

- 按 Legacy 导入门禁采纳文档 ID（合法 UUID、批内唯一、目录无冲突）可让备份恢复往返保持身份连续。被否：同一文件重复导入会撞 `duplicateID`，或被迫引入与「手动节点每次新建全新身份」不变量冲突的去重语义；且分组导出 ID 是从节点身份按 UUIDv5 派生的，采纳后再导出仍会二次哈希，完全的往返稳定本来就无法达成。
- 按端点或凭据与既有目录节点去重同样被否：ss:// 与二维码导入已是逐条新建身份、不按内容匹配（GLOSSARY「服务器导入」），导入不得静默改动既有节点。

## Consequences

- 不持久化文档 ID 与目录身份的映射。导出再导入会产生与原文件不同的 ID（服务器拿到新的手动 UUID，分组拿到新的 UUIDv5 派生值）；跨往返跟踪每台服务器状态的外部消费者会看到新身份。导出中携带的订阅供应商 UUID 在导入后不还原——导入产物是手动子树，按跨来源不变量与原订阅断开。
- SIP-008 文档的失败粒度是单个导入来源整份拒绝（共享解析器对任一无效记录拒绝整份），`ss://` 文本来源则接受有效行并逐行点名失败。两种情况下失败来源都不产生部分提交。
